# D7 量化基准：schema v3 mtime FAST 属性的时间区间查询收益

> 日期：2026-10-14 ｜ 对应架构 v2 D10 决策 ｜ 基准代码：`stcore/tests/bench_time_filter.rs`（`#[ignore]`，手动运行）

## 1. 动机

R2 把 `mtime`/`size` 从 `STORED` 升级为 `INDEXED | FAST | STORED`（schema v3），时间区间过滤得以用 tantivy `RangeQuery` 下推。升级前只能全量召回再 Rust 侧后过滤。本基准用定量数据验证该升级收益，支撑 D10「v3 为不可逆决策」的论断。

## 2. 方法

- **语料**：20,000 篇，每篇含查询词「基准」（全库命中）+ 每篇唯一 token；`mtime` 均匀分布于 730 天跨度（`BASE=1_700_000_000`，xorshift 确定性伪随机）
- **变体**：

| 变体 | 语义 | 对应 |
|---|---|---|
| C | 无时间条件分页查询 `limit=20` | 词项查询成本基线 |
| A | `search_page(..., mtime_from, mtime_to, ...)`，RangeQuery 下推 | **v3 现状** |
| B | 无条件全量召回 `limit=20000` + Rust `retain(mtime in range)` | **v2 语义模拟**（STORED-only 下 mtime 不可查询） |

- **口径**：预热 5 轮 + 计时 100 轮，报告 P50/P99/mean；每轮断言 A 的 `total` 与 B 的过滤计数相等（两种口径命中篇数一致性）
- **窗口**：10%（73 天）与 1%（7.3 天）两档，验证窗口收窄时的行为
- **环境**：本机 debug profile（`--ignored --nocapture`），`cargo test -p stcore --test bench_time_filter`

## 3. 结果

| 窗口 | 变体 | P50 (ms) | P99 (ms) | mean (ms) | 命中篇数 |
|---|---|---|---|---|---|
| 10%（73 天） | C 无过滤 | 6.311 | 9.564 | 6.471 | 20/页 |
| 10% | **A v3 RangeQuery** | **9.950** | 15.051 | 10.184 | 2,010 |
| 10% | B v2 后过滤 | 401.636 | 471.129 | 403.652 | 2,010 |
| 1%（7.3 天） | C 无过滤 | 6.281 | 9.443 | 6.437 | 20/页 |
| 1% | **A v3 RangeQuery** | **12.035** | 13.613 | 12.175 | 195 |
| 1% | B v2 后过滤 | 402.543 | 418.188 | 403.191 | 195 |

**加速比（P50）**：

- 10% 窗口：**40.4×**（401.6 ms → 10.0 ms）
- 1% 窗口：**33.4×**（402.5 ms → 12.0 ms）

一致性断言两档均通过（A total == B 过滤计数）。

## 4. 结论

1. **v3 FAST 升级收益确凿**：时间区间查询从 ~400ms 级（全库召回 + 后过滤）降至 10–12ms，P50 加速 33–40×。用户拖时间轴筛选的体验从「明显卡顿」进入「瞬时」。
2. **窗口收窄不劣化**：窗口从 10% 收到 1%（匹配篇数 2,010 → 195），A 仅从 9.95ms 增至 12.0ms（+21%），而后过滤成本与窗口宽度无关（恒为全量召回 ~400ms）。**窗口越窄、FAST 下推相对优势越大**。
3. **下推增量成本可忽略**：A 相对基线 C 的增量为 3.6–5.8ms（RangeQuery postings 遍历），相对 B 节省 98%。
4. **估算外推**（未实测，按 B 恒定 + A 近似常量）：10 万篇规模下 B 预计劣化至秒级（doc store 全量读取线性增长），A 预计仍在数十 ms 级——v3 是索引规模化的必要条件，支持「不可逆决策」定位。
